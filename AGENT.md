# ViBRo Navigator Agent Guide

Primary product requirements live in `SPECIFICATION.md` at the repository root. On the first implementation-oriented interaction in this repository, read `SPECIFICATION.md` before making changes. Use this guide together with that specification, and treat `SPECIFICATION.md` as the source of truth when implementation details or feature expectations are unclear.

For work in `docs/` or `docs-tools/`, also read `docs/AGENT.MD` and `docs-tools/README.md`. They own the website constraints and development-tooling workflow; `SPECIFICATION.md` remains the source of truth for app behavior described by the site.

## Website and documentation tooling

- `docs/` is the published static GitHub Pages site, including the homepage, changelog, legal pages, and local assets. Preserve `.nojekyll` and the runtime-dependency-free site.
- `docs-tools/` contains development-only Node.js lint, minification, and regression tooling. Keep dependencies, caches, and logs outside published `docs/`; preserve the pinned dependency versions in `package.json`. Use Node.js 20.19 or newer. This checkout has no `package-lock.json`: when dependencies are absent, run `npm install --package-lock=false` from `docs-tools/`, using `--cache .npm-cache` if needed. Use `npm ci` only if a lockfile is supplied later; do not add a lockfile or `.gitattributes` as part of routine website alignment.
- Author shared CSS and JavaScript in `docs/styles.css` and `docs/index.js`; generate `styles.min.css` and `index.min.js` with the applicable `npm run build:css`, `npm run build:js`, or `npm run build` command. Never edit generated assets by hand. Preserve generated output line endings so exact synchronization checks pass.
- Run `npm run check` from `docs-tools/` after website or tooling changes. It runs CSS/JavaScript lint, generated-asset synchronization checks, and regression tests. These are the applicable checks for website-only changes; Android flavor tests, lint, and phone installation apply when Android code or distribution behavior also changes.
- When a delivered CSS or JavaScript asset changes, bump its cache query consistently across all six public HTML pages. Keep legal content and unrelated website content intact unless the user requests changes, and follow `docs/AGENT.MD` for visual and interaction constraints.
- Website design and tooling changes belong in the website guidance. Update `SPECIFICATION.md` only when app behavior, product requirements, or distribution expectations change; keep public app claims aligned with it.

## Project rules

- When implementing a user request, do not stop at the narrowest change that merely appears to work. Implement the most correct solution for the product and architecture, accounting for realistic edge cases, failure modes, lifecycle states, flavor boundaries, and existing contracts before closing the task.
- Keep repository documentation aligned with the code when relevant changes are made. Update `SPECIFICATION.md` when product behavior, requirements, or user-visible flows change. Update `AGENT.md` when architecture, guardrails, workflows, or coding expectations change. Do not make doc-only churn for code changes that do not affect those areas.
- Keep README/about content aligned at the product-description level. `README.md` and `about_short_description` in `strings.xml` should stay consistent about the app's purpose and core behavior, but they do not need to be literal copies of each other.
- When release/distribution mechanics change, keep `.github/workflows/fdroid-ready.yml`, `.github/workflows/fdroid-submit.yml`, `fastlane/metadata/android/en-US/...`, `fdroid/vibro.navigator.yml`, and `fdroid/SUBMISSION.md` aligned so the maintainer-facing F-Droid process remains accurate.
- At the end of implementation work, always ask whether to do a fresh recompile and install on a connected phone if one is available, and if there are next-step suggestions, propose those as well.

## Practical review checklist

- Does the change keep the app dependency-light?
- Are new strings localized through `strings.xml`?
- Does the change preserve offline-first behavior?
- Does the change work in both portrait and landscape?
- Does navigation still work in background and with screen off?
- Are permissions/settings prompts still reachable for location, notifications, and battery optimization?
- Are BRouter profile selection and route calculation still intact?
- Would the resulting turn guidance still be safe to trust without looking at a map?

## Stack and build

- Single-module Android app at `app/`
- Language: Java only
- UI base: platform `Activity` + platform widgets/dialogs, with `androidx.core` kept for compatibility helpers
- Keep navigation back handling compatible with predictive back using platform callbacks; do not migrate the app shell to `ComponentActivity` unless explicitly requested
- Gradle: `9.8.1`
- Android Gradle Plugin: `9.4.1`
- Java toolchain: `17`
- SDKs in repo today: `compileSdk 37`, `targetSdk 37`, `minSdk 23`
- Runtime dependencies are intentionally minimal in the common/F-Droid code path: `androidx.core`
- The app has two distribution flavors: `fdroid` and `gplay`
- Google Play Services is allowed only in the `gplay` source set/dependency graph. Keep F-Droid and common source sets free of Google Play Services classes, API clients, and build requirements.
- Android for Cars App Library dependencies and Android Auto manifest/resources are allowed only in the `gplay` source set/dependency graph. Android Auto must use templated `CarAppService` screens and may render the phone-style landscape navigation UI only by drawing onto an Android for Cars navigation surface; do not try to host the phone `Activity` or raw phone layout on the car display.
- Use focused adapter boundaries for Android framework APIs, Google/third-party SDKs, and other external APIs when the API has permission checks, OS/version guards, callbacks, deprecations, flavor-specific implementations, lifecycle coupling, or makes plain JVM testing difficult. Keep external API calls and raw external types inside the adapter package/source set; expose app-owned ports, value objects, and callback interfaces to the rest of the app. Prefer nesting or inlining stateless one-consumer helpers inside their owning adapter or entry-point shell; split them into top-level adapters only when they are shared, stateful, independently testable, or meaningfully reduce framework leakage. Avoid broad "API service" facades: name adapters by capability, such as `android/location`, `android/foreground`, `android/power`, `android/startup`, or `nav/voice`.
- Android location framework APIs are allowed only in the `vibro.navigator.android.location` package, including flavor and test source sets. Outside that package, do not import or reference `android.location.*`, `LocationManager`, `LocationListener`, or `GnssStatus`; use app-owned ports/value objects such as `NavigationLocation`, `NavigationLocationListener`, `NavigationLocationProvider`, `NavigationGnssTracker`, and `NavigationLocationProviders`.
- Android heading-sensor framework APIs are allowed only in `vibro.navigator.android.sensor`. Navigation and About-page code should use app-owned heading samples, accuracy constants, and diagnostics snapshots rather than importing `android.hardware.Sensor*` or `SensorManager` directly.
- Android monotonic elapsed-time reads belong behind `nav/time/ElapsedRealtimeClock`, with Android `SystemClock.elapsedRealtime()` provided by `android/time/AndroidElapsedRealtimeClock`. Navigation/orientation and Auto/UI countdown code should consume the app-owned clock so tests and display policy stay independent of Android static time APIs.
- Android main-thread scheduling and delayed callbacks belong behind `dispatch/TaskScheduler`, with Android `Handler` wiring provided by `android/dispatch/AndroidTaskScheduler`. Use its animation-frame callback for compass transitions so phone and Android Auto drawing follows display refresh. Non-adapter navigation, map, POI, and About helpers should depend on the scheduler port instead of importing `android.os.Handler` directly. Focused Android adapters may pass a local `Handler` directly to framework registration or timeout APIs when the `Handler` does not leave the adapter and no shared scheduling policy is involved.
- Android storage/document/provider helpers that are shared across app logging, SAF picker setup, BRouter profile discovery, and BRouter segment random reads belong in focused `android/storage` adapters rather than duplicating `DocumentsContract`, `StorageManager`, or `Environment` calls in feature logic. Keep one-consumer BRouter package-manager and persisted-URI grant probes local to the `android/brouter` repository wiring unless they become shared or independently complex.
- Keep the Android-version choice for BRouter profile setup/status in `android/brouter/AndroidBRouterProfilesStorageAccess`: Android 6–9 reuse street storage's runtime read permission; later versions use persisted folder access. Reuse existing direct document-file discovery rather than adding a second profile file reader, and derive folder instructions from the same URI passed to the picker.
- BRouter Android service integration and Android-backed profile/segment repository wiring belong behind the focused `android/brouter` adapter. Keep route-parameter `Bundle` creation, compressed-response Android decoding, install intents, and `BRouterProfileDependencies`/`BRouterSegmentDependencies` construction there; common routing code should use app-owned `BRouterRouteClient`, `BRouterRouteRequest`, profile dependency access contracts, and segment dependency access contracts. The external BRouter AIDL contract and minimal `btools.routingapp.BRouterServiceConnection` compatibility shim may live under the `btools.routingapp` package because the service contract expects that package, but app-owned code should reach them only through `android/brouter`.
- Default Android route-executor wiring belongs in `android/routing`, including Android wake-lock construction and Android BRouter client construction. `nav/routing/NavigationRouteExecutor` should stay independent of Android `Context` and call an already-wired route calculator.
- Android Auto component enablement uses package-manager state and is owned by the gplay distribution bridge unless it grows beyond the current small component toggle. Small car-mode framework adapters may live under the gplay `android/automotive` package; Auto template/surface code may stay under the gplay `auto` package, but delayed UI ticks should use `dispatch/TaskScheduler` rather than raw Android `Handler` wiring.
- Android TextToSpeech engine and raw `Voice` usage belongs in `nav/voice`. About-page speech settings should consume `NavigationVoiceOption`, `NavigationTextToSpeechSettingsClient`, and `NavigationTextToSpeechSettingsLauncher` rather than owning TTS engine lifecycle or raw voice objects.
- Keep `gplay` listed before `fdroid` in `productFlavors` so default debug variant selection includes the fused-location implementation.

## Test strategy

- Apply the 100% code-coverable principle: production decisions, policy thresholds, parsers, planners, and formatting rules should expose a plain JVM-testable path. When Android objects are only data carriers, add a small value-object or overload boundary so the decision code can be tested without Robolectric.
- Prefer JVM tests. Use Robolectric when Android lifecycle coverage is needed.
- Keep Robolectric limited to tests that actually need Android framework execution: Activity/Service lifecycle, resources, `Context`/`SharedPreferences`, package manager/intent resolution, framework services/shadows, view drawing, or Android SDK stubs that are not executable in plain local tests.
- When a framework or SDK call only supports integration-style testing, put that call behind a narrow app-owned port and unit-test the policy/decision code against fakes. Robolectric tests should validate adapter wiring only where framework execution is the behavior under test.
- Do not add emulator/device requirements to the core automated suite unless explicitly requested.
- Add or update tests when you change navigation state, rerouting, route parsing, voice-hint mapping, geometry helpers, or user-visible behavior.
- Keep lifecycle rules, heuristics, planners, route export serialization, and policy thresholds in small helpers when practical so they stay directly unit-testable.
- Keep focused coverage around navigation startup/preflight, request serialization, reroute heuristics, blocked-road escalation, turn progression, route-request lifecycle handling, foreground-notification monitoring, route callback handoff, turn-event dispatch, and state broadcasting.
- Changes to pause/resume behavior should add or update focused JVM coverage for session state and any service-policy decisions that depend on paused navigation.
- `.\gradlew.bat complexityCheck` runs the enforced PMD maintainability baseline over production and JVM test Java sources, including flavor source sets. The task has a zero-violation baseline and should fail on any reported violation across complexity, size, coupling, nested-flow, dead-code, duplicate-literal, and related maintainability rules. Treat violations as refactor candidates, with priority for navigation/routing safety logic and frequently edited classes. Prefer fixes that remove real reasoning burden, such as extracting named handoff contracts or policy helpers; do not add indirection solely to silence coupling warnings on thin shell/coordinator classes.
- Avoid `@SuppressWarnings` by default. Always first check whether the warning can be reasonably removed by simplifying logic, tightening types, extracting a focused helper, using a min-SDK-safe API boundary, or adding focused coverage. Add or keep a suppression only when the warning is unavoidable, the compatibility path is intentional, or the fix would make the code less clear, less safe, or incompatible with `minSdk 23`; keep any remaining suppression narrowly scoped.
- Before the final verification tests for an implementation task, review the diff for newly introduced technical debt: unexplained timing constants, unnecessary abstractions, hidden lifecycle/state coupling, duplicated policy, broad catch-all helpers, fragile test waits, or deviations from the package ownership rules. Fix avoidable debt before running the final test pass so verification covers the cleaned-up implementation.
- For tap, click, and switch handlers, preserve first-frame visual feedback. Do not run file I/O, package-manager/component toggles, diagnostics/sensor/location probes, database import/export, network work, or broad re-rendering directly in the listener. Let the pressed/checked state render first, defer heavier effects through `dispatch/TaskScheduler` past the relevant control animation, and add a focused flush path before lifecycle exits or export/import flows when persistence is delayed.
- After any code update, always run the relevant flavor tests and lint before closing the task. Treat test, lint, Java compiler, Gradle, and PMD warnings as actionable and address them in the best meaningful way before closing: prefer real fixes, API-version-safe alternatives, small compatibility helpers, or focused tests over suppressions; use suppressions such as `@SuppressWarnings("deprecation")` only when the deprecated API is intentionally required for min-SDK compatibility, framework callback coverage, or Robolectric/test visibility and no better supported path exists. For distribution-sensitive changes, run `.\gradlew.bat lintFdroidDebug lintGplayDebug testFdroidDebugUnitTest testGplayDebugUnitTest assembleFdroidRelease assembleGplayRelease`.
- Refactors that only move unchanged wiring into thin helpers do not need new tests by default. Behavior changes do.

## Editing guidance

Use these guardrails as a change-specific checklist before editing or reviewing related areas. The detailed ownership map is in the Architecture section.

- Keep background route computation separated from main-thread state mutation. Preserve `nav/routing/NavigationRouteExecutor` rather than inlining thread management back into `NavigationService`.
- Keep BRouter transient-failure classification in `nav/routing/BRouterTransientFailureClassifier`, retry attempt/delay behavior in `NavigationRouteRetryPolicy`, and the default BRouter adapter in `nav/routing/NavigationBRouterRouteCalculator` so `NavigationRouteExecutor` stays focused on route task submission, callback handoff, executor shutdown, and wake-lock scoping.
- Keep Android service concerns delegated through the existing foreground/location/power/dispatch/broadcast helpers and Android adapters, and keep `NavigationSession` as a coordinator over focused session collaborators.
- Do not add a wake-lock renewal loop or reintroduce a session-lifetime wake lock to keep navigation alive; if a path needs a wake lock, scope it to the shortest critical section that actually needs CPU residency.
- If you change reroute thresholds, polling cadence, turn-alert timing, blocked-road escalation, or route-request lifecycle behavior, update the corresponding `nav/` tests.
- If you change guidance confidence rules, keep map-free use in mind and update tests around bearing trust, forward-look route bearing, direction-of-progress, turn suppression, and duplicate/imminent alert behavior.
- If you change display heading selection, cover routed and round-trip movement, straight-line and route-start/native/synthetic beelines, bearing accuracy and freshness, compass fallback, beeline-to-route transitions, and heading-only refreshes. Preserve startup compass tracking and the stationary compass activation/continuous-tracking contract in specification section 4.5.2.
- Full display snapshots must carry separate wall and elapsed time through `nav/time/NavigationDisplayTime`. Use elapsed time for heading freshness, stationary gates and compass radius transitions; reserve wall time for arrival labels. Regression fixtures must include distinct clock values and interleaved structural/heading updates so synthetic shared-clock tests cannot conceal source switching.
- Keep route-start-to-native/synthetic-beeline activation atomic in `NavigationRouteDirectGuidanceEvaluator`: select the outgoing target before initial road-turn events or display state. `NavigationRouteBeelineState` owns reached-radius activation bounded by matched progress. Clear display-course history on confirmed stops in `NavigationLocationMotionModel`; keep native speed confirmation in `NavigationStationarityTracker` separate from heading accuracy and reroute bearing gates. Accepted-fix diagnostics should reuse `NavigationLocationFormatter` and include both native accuracy fields and resolved motion state.
- Active beeline direction cues belong in `nav/session/CompassDisplayMemory`, selected by `NavigationSessionRouteDisplayState` using the active direct-guidance target. Give that live absolute target bearing precedence over road/stationary cues and clear cached maneuver cues at the handoff; test intermediate-stop and return-leg progression independently of display heading.
- Keep the beeline-to-road heading handoff in nav/session/NavigationBeelineHeadingHandoff, coordinated by NavigationSessionRouteState and updated by accepted route evaluations independently of visible UI snapshots. Retain the location-heading policy through BACKWARD, STALLED and UNKNOWN progress until a later stable moving road evaluation confirms FORWARD with NavigationRouteProgressTracker. NavigationSessionStateBuilder must share that source policy for full and heading-only refreshes; Carry NavigationHeadingSource explicitly through heading selections, compass snapshots and viewport/cache copies, with full and heading-only state composition in NavStateCompassHeadingComposer. NavigationCompassModeController and NavigationCompassHeadingTransition must animate actual route/location/compass source changes over 500 ms using existing phone/Auto frames; a beeline-exit guidance-mode change alone must not trigger rotation. Held headings retain their source, same-source live updates do not restart rotation, and pause/geometry reset cancels it. Do not alter direct-guidance cues, stationary compass gates, reroute evidence or location cadence.
- Keep route-display smoothing in `nav/orientation/NavigationRouteDisplayHeadingResolver`, separate from the expected bearing used for deviation checks. Around maneuvers, retain the original forward-look bearing so the view rotates gradually through the turn; do not clip that bearing at maneuver points or hold the incoming heading until the maneuver. Routed location-heading disagreement confirmation belongs in `nav/session/NavigationRouteHeadingFallback`; it must use independently timed location evidence, retain source accuracy, clear across route/motion lifecycle transitions, and never relax reroute confidence or request additional fixes.
- If you change surrounding streets, keep the limits and lifecycle contract in specification section 4.3.2 aligned. Preserve coverage for spatial sampling independent of rd5 cell order, decoded-cell reuse and revision invalidation, cache-budget reload prevention, cancellation/stale-result rejection, and heading-only path reuse. Validate both flavors with minSdk 23-safe Java APIs; do not infer measured battery savings from reduced operation counts.
- Per-type surrounding-street visibility belongs in `settings/AppCompassStreetTypeSettings`, the About-page picker in `about/AboutSurroundingStreetTypes`, and extraction filtering in `brouter/BRouterStreetSegmentCollector` before spatial sampling/session caching. `BRouterStreetFileLoader` handles local file reads while `BRouterSegmentsRepository` owns the reusable complete decoded-cell cache and source discovery. Changing the selection must invalidate filtered overlay chunks and reject stale loads; keep the complete decoded-cell cache reusable across selections. Keep new `CompassStreetType` values appended because packed decoded cells store enum ordinals; BRouter route values are distinct, while all railway values and all waterway values each remain one selectable type. Speed filtering remains display-side and guidance is unaffected.
- If you change navigation request intent extras, update `android/intent/AndroidNavigationRequestIntentContract` first and keep resume/start flows serialized through it instead of hand-copying extras.
- If you change startup permission/settings/battery-optimization flow, keep `nav/ui/NavigationActivity` thin, keep Android preflight orchestration and settings intents in `android/startup/AndroidNavigationPreflight`, keep raw location provider-state probes in `android/location`, and update the startup/lifecycle tests.
- If you change BRouter request parameters, response parsing, or voice-hint mapping, inspect `brouter/`, `nav/routing/`, `nav/route/`, and `nav/directions/` together and keep mode-9 coverage aligned.
- If you change round-trip setup direction behavior, keep `RoundTripDirectionInput`, `MainActivityRoundTripDirectionController`, `MainActivityRoundTripRequestFactory`, `MainRoundTripDirectionCompassView`, `NavigationRequest`, `AndroidNavigationRequestIntentContract`, `NavigationRouteRequestSnapshot`, executor/manager/retry wiring, and BRouter request/bundle tests aligned. The compact round-trip compass should preserve navigation-compass cue semantics while keeping its visible status color: status ring and accuracy guide strokes should match the white heading arrow, and cardinal letters should stay visually separated from tick marks.
- If you change POI search or incoming intent handling, preserve coordinate entry, empty-field history suggestions, history-before-online precedence from the first typed character, shared search dispatch, and history behavior for externally opened locations.
- If you add or change direct Android framework, Google SDK, AndroidX service, BRouter/document-provider, notification, TTS, sensor, or other external API access, first decide whether a focused adapter is meaningful. Also verify fused GMS references remain isolated to `app/src/gplay/java/vibro/navigator/android/location` and `app/src/testGplay/java/vibro/navigator/android/location`.
- If you change fused location, Google POI search, Android Auto, or distribution bridges, verify Google and Android for Cars references remain isolated to `app/src/gplay` and `app/src/testGplay`, and verify the F-Droid runtime classpath does not gain Play Services or Android for Cars dependencies.
- If you change Android Auto behavior, keep the Auto package as a template adapter over `NavigationService`/`NavState`, keep Android car-mode framework adapters under `app/src/gplay/java/vibro/navigator/android/automotive`, keep Auto strings in `app/src/gplay/res/values`, keep manifest, surface permission, and `automotive_app_desc.xml` declarations under `app/src/gplay`, and run both `assembleGplayDebug` and an F-Droid build to catch flavor leakage.
- If you change the map picker, preserve the no-external-library constraint, OSM raster tile rendering, current-location fallback when a field has no coordinates yet, restored-selection behavior across rotation, and the icon-only control layout. For map POIs, preserve user-initiated category discovery, single active category behavior, category counts, cached marker reuse from discovery responses, and missing-bounds-only Overpass fetches on pan/zoom.
- If you change logging, preserve shared `buildLogPrefix` formatting, log-enabled gating, selected-folder session ownership, and `AndroidLogFolderWriter` UTF-8-safe trimming. Keep legacy file utilities available for existing files without redirecting new output.
- If you change the stored data backup format, update `settings/AppDataBackup`, its tests, and the specification together so import/export compatibility and included data stores remain explicit.
- When extracting helpers around Android APIs, preserve lint-visible SDK guards with `@RequiresApi`, guarded callers, or min-SDK-safe overloads. In particular, avoid newer Java/Android overloads such as `URLEncoder.encode(String, Charset)` unless desugaring/minSdk support is already verified by flavor lint.
- If you change icon/theme/about assets, preserve the app identity: minimal, dark-by-default, vibration-first navigation, with light mode treated as an optional user setting.

## Architecture

- Phone compass gesture adjustments belong in `nav/orientation/NavigationCompassGestureState`, layered after `NavigationCompassModeController` resolves the display viewport and before sending that viewport to the street-overlay binder. `nav/compass/ui/NavigationCompassTouchListener` separates two-finger pinch/tilt streams from single-finger view gestures. `NavigationCompassSingleTouchListener` recognizes directional swipes and double taps, while the touch listener dispatches the accessible `performClick` action; horizontal travel policy belongs in the JVM-testable `NavigationCompassSwipeSequence`. Left swipes advance and right swipes reverse the shared mode cycle. Double-tap timing and movement policy belong in `nav/orientation/NavigationCompassTapSequence`, with pressed feedback in `nav/compass/ui/NavigationCompassTapListener`. Both phone compass surfaces share one adjustment state through `NavigationCompassSurfaces`; keep tilt changes independent of the fixed prepared perspective viewport so tilt frames reuse geometry. Android Auto shares the mode and adjustment state policies through `ViBRoAutoCompassPainter`; `ViBRoAutoGestureSequence` adapts host scroll/scale deltas using the shared swipe policy and a platform double-tap quiet interval because the car API has no raw pointer/end events. Host double tap is a scale callback and zooms; single click cycles views, horizontal scroll cycles in either direction, and vertical scroll adjusts 3D inclination. Require the API-2 `Action.PAN` map strip for host callbacks while retaining API-1 template compatibility. Reset Auto display/input state on navigation clear and surface closure, and publish the adjusted street viewport.

- The compass tap cycle belongs in `nav/orientation/NavigationCompassModeController`; phone and Android Auto must use that same mode policy. Tap radius smoothing belongs in `NavigationCompassUiRadiusTransition`, and the short 2D/3D tilt animation belongs in `NavigationCompassPerspectiveTransition`. `CompassPerspectiveScale` derives a fixed expanded route/street viewport and forward distance references for the selected projection; keep the prepared route range, projected route paths, and street paths reusable through tilt frames instead of rebuilding them on every frame. Both transforms belong in `NavigationCompassPerspective`: the original orthographic tilt uses affine vertical compression with an optional center offset, while the default Perspective 3D view uses a homography with positive depth throughout a clipped prepared ground plane. Preserve depth-independent widths and parallel lines in the orthographic projection. Synchronize the preference with the mode controller before resolving phone/Auto viewports; the renderer must use the same source multiplier so local route scale stays consistent. `NavigationCompassView` applies the transform to route, streets, markers, heading arrow, and compact heading accuracy lines; distance text and orientation cues stay flat. The deferred projection switch/import refresh is owned by `about/AboutCompassProjectionSettings`. Outer ring tick/cardinal drawing belongs in `NavigationCompassOuterRingRenderer`.
- A null compass snapshot is a temporary geometry gap, not a navigation reset: mode and gesture controllers must retain user adjustments while releasing geometry caches and cancelling heading/radius animations. Use their explicit `reset()` methods for Auto navigation clear/surface closure; phone controllers are scoped to each navigation screen. Navigation domain packages are intentionally split by reasoning boundary: `nav/route` holds route data and geometry primitives; `nav/routing` owns BRouter route execution and request lifecycle; `nav/guidance` owns route progress, reroute policy, straight-line wrong-direction evidence, turn planning, and update cadence; `nav/location` owns GPS/provider and motion state; `nav/orientation` owns heading use and stationary turn-to-face-route advice; `nav/compass/ui` owns compass drawing; `nav/streets` owns battery-bounded surrounding-street refresh policy and background extraction orchestration; `nav/foreground` owns foreground notification/screen-interactivity contracts and monitoring policy while Android notification/channel/receiver wiring lives in `android/foreground`; `nav/voice` owns spoken maneuver text and Android TTS engine lifecycle; `nav/power` owns short wake-lock scopes through the app-owned `NavigationWakeLock` port, app-owned battery snapshots, and snapshot freshness policy for navigation trip statistics, while battery-change receiver plus Android `PowerManager`/`BatteryManager` access lives in `android/power`; `nav/export` owns active-route GPX serialization while `android/export` owns GPX chooser content URIs and GPX output writing; `nav/model`, `nav/presentation`, `nav/format`, and `nav/policy` hold shared domain/display contracts, Android/resource-aware display-state assembly, user-visible formatting, and lifecycle policy. App-wide incoming map/share parsing lives in `intent/`; entry-point shells may extract Android `Intent` action/data/text directly before handing strings to that parser, while navigation request extras wiring remains in `android/intent`. App-wide diagnostics logging lives in `logging/`.
- About-page diagnostics and settings helpers live in `about/` and are split between `AboutDiagnosticSection` for diagnostic lifecycle/rendering, `AboutPermissionStatusRows` for required-access status rows and settings redirects, `AboutSensorStatusFormatter` for sensor/live-input status orchestration over Android location/sensor adapters, `AboutSensorValueFormatter` for pure location diagnostic value formatting, `AboutManeuverVoiceSettings` for speech-direction voice-listing UI over the `nav/voice` TTS settings client, and `NavigationTextToSpeechSettingsLauncher` for Android Text-to-speech settings intents. Android location diagnostics and GNSS satellite tracking for the About page belong behind `android/location/AndroidLocationDiagnostics`, not in `about/`; Android heading-sensor registration and rotation-vector formatting belong behind `android/sensor/AndroidHeadingSensorDiagnostics`, not in `about/`. Required-access diagnostics should reuse `nav/startup/NavigationPreflight` status contracts, `android/startup/AndroidNavigationPreflight` platform inspection/intents, and `android/startup/AndroidNavigationSettingsLauncher` rather than duplicating permission or OEM settings-redirect rules. Shared heading-sensor capability selection belongs in `sensor/HeadingSensorSupport`.
- `logging/AppLogger` is the shared logging facade. Single-line and multiline writes use the same `buildLogPrefix` formatting and one active `AppLogDestination`. Keep selected destination resolution in `AndroidOutputStorage`, and stream publication and UTF-8 trimming in `AndroidLogFolderWriter`. Missing access or failed writes disable saving; never create a fallback session or copy history. `AndroidOutputPermissionRequest` owns selected-folder permission requests, verification, cancellation, and recreation state for save switches and manual GPX export. `AboutOutputSavingSettings` serializes saving-setting changes and flushes persistence before lifecycle exits or database backups.
- Automatic GPX/log destinations are owned by android/storage/AndroidOutputStorage and AndroidOutputDestination. Use only the selected MediaStore.Downloads volume on Android 10+, direct phone Downloads with WRITE_EXTERNAL_STORAGE on Android 6–9, or an SD Downloads ancestor grant for legacy cards. AppOutputStorageSettings keeps the SD preference/grant device-local in output_folders, excluded from backups. AndroidOutputStorageVolumes detects stable removable slots and rejects unsupported MediaStore volumes; exclude transient USB storage. AndroidOutputStorageAccess validates SD roots/Download/ViBRo ancestors, reuses persisted read/write grants, and verifies both fixed destinations before enabling storage. AndroidOutputFile owns stream creation, pending publication, partial-file cleanup and sharing. Missing access or write failures disable saving without redirecting output. AndroidOutputPermissionPrompt owns the Android permission UI; AndroidOutputPermissionRequest owns verification and pending-result lifecycle. GPX exports/deletion share AndroidRouteGpxActions' worker. Delete only generated filenames in the confirmed destination token, plus MediaStore ownership. Close/restart logs under AppLogger's lock. AboutOutputStorageSwitch handles SD access independently of saving switches; AboutOutputFolderStatusRows checks selected folders/access off the UI thread on Android 6–9 and shows folder names with access status. AboutOutputFolderSettings offers Open/Delete/OK actions, and AndroidOutputStorageBrowser launches AndroidOutputBrowserActivity with a separate task affinity and NEW_TASK/CLEAR_TOP so ViBRo stays reachable in Recents. This transparent non-exported host launches the system document picker at the selected folder where supported, owns picker results/recreation and opens selected files with temporary read access; avoid OEM directory viewers that silently close. Preserve old files when removing custom folder choices.
- Always-on crash and interrupted-navigation diagnostics use `logging/AppExitDiagnostics` through `AppLogger.anomaly`. Reuse the standard timestamped log-file selection and system-details first entry even when detailed logging is disabled. Keep Android 11+ `ApplicationExitInfo` access in `android/logging/AndroidProcessExitReader`, and do not claim that an OEM battery optimizer caused an exit unless Android reports that cause.
- Settings database export/import lives in `settings/AppDataBackup` and is launched from the About-page Settings section through Android document picker intents. Keep the backup boundary limited to app-managed stored preferences such as POI history, saved routes, app settings, logging preference, BRouter profile selections, and BRouter profile parameter overrides; do not add broad storage permissions for backup files.

## Local config

- Optional Google key for the `gplay` flavor only: save a Google Maps key in the app's About settings, validate non-empty keys through Google Maps Geocoding before marking them valid, and enable Google search only for saved valid keys. Do not bundle Google API keys into the APK.
- BRouter must be installed on the device as `btools.routingapp`
- The app may use a user-selected document tree for external custom `.brf` profiles
- Destination/stop map picking currently requires only platform WebView plus network access to `tile.openstreetmap.org`; do not replace it with an external map dependency unless explicitly requested
- `local.properties` is developer-local configuration. Do not make release or F-Droid flows depend on committed machine-specific values.
- Optional behavior logs are written only in `Download/ViBRo/logs` on the phone or selected SD card. Check `/sdcard/Download/ViBRo/logs/` or `/storage/<card-id>/Download/ViBRo/logs/`. Missing folder access or unavailable selected storage switches logging off without redirecting output.
