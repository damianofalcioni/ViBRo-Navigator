# ViBRo Navigator Agent Guide

Primary product requirements live in `SPECIFICATION.md` at the repository root. On the first implementation-oriented interaction in this repository, read `SPECIFICATION.md` before making changes. Use this guide together with that specification, and treat `SPECIFICATION.md` as the source of truth when implementation details or feature expectations are unclear.

## Project rules

- When implementing a user request, do not stop at the narrowest change that merely appears to work. Implement the most correct solution for the product and architecture, accounting for realistic edge cases, failure modes, lifecycle states, flavor boundaries, and existing contracts before closing the task.
- Keep repository documentation aligned with the code when relevant changes are made. Update `SPECIFICATION.md` when product behavior, requirements, or user-visible flows change. Update `AGENT.md` when architecture, guardrails, workflows, or coding expectations change. Do not make doc-only churn for code changes that do not affect those areas.
- Keep README/about content aligned at the product-description level. `README.md` and `about_short_description` in `strings.xml` should stay consistent about the app's purpose and core behavior, but they do not need to be literal copies of each other.
- When release/distribution mechanics change, keep `.github/workflows/fdroid-ready.yml`, `.github/workflows/fdroid-submit.yml`, `fastlane/metadata/android/en-US/...`, `fdroid/vibro.navigator.yml`, and `fdroid/SUBMISSION.md` aligned so the maintainer-facing F-Droid process remains accurate.
- At the end of implementation work, always ask whether to do a fresh recompile and install on a connected phone if one is available, and if there are next-step suggestions, propose those as well.

## Practical review checklist

- Does the change keep the app dependency-light?
- Are new strings localized through `strings.xml`?
- Does the change preserve offline-first behavior?
- Does the change work in both portrait and landscape?
- Does navigation still work in background and with screen off?
- Are permissions/settings prompts still reachable for location, notifications, and battery optimization?
- Are BRouter profile selection and route calculation still intact?
- Would the resulting turn guidance still be safe to trust without looking at a map?

## Stack and build

- Single-module Android app at `app/`
- Language: Java only
- UI base: platform `Activity` + platform widgets/dialogs, with `androidx.core` kept for compatibility helpers
- Keep navigation back handling compatible with predictive back using platform callbacks; do not migrate the app shell to `ComponentActivity` unless explicitly requested
- Gradle: `9.5.1`
- Android Gradle Plugin: `9.2.0`
- Java toolchain: `17`
- SDKs in repo today: `compileSdk 37`, `targetSdk 37`, `minSdk 21`
- Runtime dependencies are intentionally minimal in the common/F-Droid code path: `androidx.core`
- The app has two distribution flavors: `fdroid` and `gplay`
- Google Play Services is allowed only in the `gplay` source set/dependency graph. Keep F-Droid and common source sets free of Google Play Services classes, API clients, and build requirements.
- Android for Cars App Library dependencies and Android Auto manifest/resources are allowed only in the `gplay` source set/dependency graph. Android Auto must use templated `CarAppService` screens and may render the phone-style landscape navigation UI only by drawing onto an Android for Cars navigation surface; do not try to host the phone `Activity` or raw phone layout on the car display.
- Use focused adapter boundaries for Android framework APIs, Google/third-party SDKs, and other external APIs when the API has permission checks, OS/version guards, callbacks, deprecations, flavor-specific implementations, lifecycle coupling, or makes plain JVM testing difficult. Keep external API calls and raw external types inside the adapter package/source set; expose app-owned ports, value objects, and callback interfaces to the rest of the app. Avoid broad "API service" facades: name adapters by capability, such as `android/location`, `android/foreground`, `android/power`, `android/startup`, or `nav/voice`.
- Android location framework APIs are allowed only in the `vibro.navigator.android.location` package, including flavor and test source sets. Outside that package, do not import or reference `android.location.*`, `LocationManager`, `LocationListener`, or `GnssStatus`; use app-owned ports/value objects such as `NavigationLocation`, `NavigationLocationListener`, `NavigationLocationProvider`, `NavigationGnssTracker`, and `NavigationLocationProviders`.
- Android heading-sensor framework APIs are allowed only in `vibro.navigator.android.sensor`. Navigation and About-page code should use app-owned heading samples, accuracy constants, and diagnostics snapshots rather than importing `android.hardware.Sensor*` or `SensorManager` directly.
- Android monotonic elapsed-time reads belong behind `nav/time/ElapsedRealtimeClock`, with Android `SystemClock.elapsedRealtime()` provided by `android/time/AndroidElapsedRealtimeClock`. Navigation/orientation and Auto/UI countdown code should consume the app-owned clock so tests and display policy stay independent of Android static time APIs.
- Android main-thread scheduling and delayed callbacks belong behind `dispatch/TaskScheduler`, with Android `Handler` wiring provided by `android/dispatch/AndroidTaskScheduler`. Non-adapter navigation, map, POI, and About helpers should depend on the scheduler port instead of importing `android.os.Handler` directly.
- Android storage/document/provider and package-manager probes that support BRouter profile discovery, app logging storage, SAF picker setup, persisted URI grants, and package availability belong in the focused `android/storage` and `android/packageinfo` adapters rather than duplicating `DocumentsContract`, `StorageManager`, `Environment`, or `PackageManager` calls in feature logic.
- BRouter Android service integration belongs behind the focused `android/brouter` adapter. Keep AIDL service binding, `IBRouterService`, route-parameter `Bundle` creation, compressed-response Android decoding, and BRouter install intents there; common routing code should use app-owned `BRouterRouteClient` and `BRouterRouteRequest` contracts.
- Default Android route-executor wiring belongs in `android/routing`, including Android wake-lock construction and Android BRouter client construction. `nav/routing/NavigationRouteExecutor` should stay independent of Android `Context` and call an already-wired route calculator.
- Android Auto component enablement uses package-manager state and belongs in the gplay `android/auto` adapter. Auto template/surface code may stay under the gplay `auto` package, but delayed UI ticks should use `dispatch/TaskScheduler` rather than raw Android `Handler` wiring.
- Android TextToSpeech engine and raw `Voice` usage belongs in `nav/voice`. About-page speech settings should consume `NavigationVoiceOption`, `NavigationTextToSpeechSettingsClient`, and `NavigationTextToSpeechSettingsLauncher` rather than owning TTS engine lifecycle or raw voice objects.
- Keep `gplay` listed before `fdroid` in `productFlavors` so default debug variant selection includes the fused-location implementation.

## Test strategy

- Apply the 100% code-coverable principle: production decisions, policy thresholds, parsers, planners, and formatting rules should expose a plain JVM-testable path. When Android objects are only data carriers, add a small value-object or overload boundary so the decision code can be tested without Robolectric.
- Prefer JVM tests. Use Robolectric when Android lifecycle coverage is needed.
- Keep Robolectric limited to tests that actually need Android framework execution: Activity/Service lifecycle, resources, `Context`/`SharedPreferences`, package manager/intent resolution, framework services/shadows, view drawing, or Android SDK stubs that are not executable in plain local tests.
- When a framework or SDK call only supports integration-style testing, put that call behind a narrow app-owned port and unit-test the policy/decision code against fakes. Robolectric tests should validate adapter wiring only where framework execution is the behavior under test.
- Do not add emulator/device requirements to the core automated suite unless explicitly requested.
- Add or update tests when you change navigation state, rerouting, route parsing, voice-hint mapping, geometry helpers, or user-visible behavior.
- Keep lifecycle rules, heuristics, planners, route export serialization, and policy thresholds in small helpers when practical so they stay directly unit-testable.
- Keep focused coverage around navigation startup/preflight, request serialization, reroute heuristics, blocked-road escalation, turn progression, route-request lifecycle handling, foreground-notification monitoring, route callback handoff, turn-event dispatch, and state broadcasting.
- Changes to pause/resume behavior should add or update focused JVM coverage for session state and any service-policy decisions that depend on paused navigation.
- `.\gradlew.bat complexityCheck` runs the enforced PMD maintainability baseline over production and JVM test Java sources, including flavor source sets. The task has a zero-violation baseline and should fail on any reported violation across complexity, size, coupling, nested-flow, dead-code, duplicate-literal, and related maintainability rules. Treat violations as refactor candidates, with priority for navigation/routing safety logic and frequently edited classes. Prefer fixes that remove real reasoning burden, such as extracting named handoff contracts or policy helpers; do not add indirection solely to silence coupling warnings on thin shell/coordinator classes.
- Avoid `@SuppressWarnings` by default. Always first check whether the warning can be reasonably removed by simplifying logic, tightening types, extracting a focused helper, using a min-SDK-safe API boundary, or adding focused coverage. Add or keep a suppression only when the warning is unavoidable, the compatibility path is intentional, or the fix would make the code less clear, less safe, or incompatible with `minSdk 21`; keep any remaining suppression narrowly scoped.
- After any code update, always run the relevant flavor tests and lint before closing the task. Treat test, lint, Java compiler, Gradle, and PMD warnings as actionable and address them in the best meaningful way before closing: prefer real fixes, API-version-safe alternatives, small compatibility helpers, or focused tests over suppressions; use suppressions such as `@SuppressWarnings("deprecation")` only when the deprecated API is intentionally required for min-SDK compatibility, framework callback coverage, or Robolectric/test visibility and no better supported path exists. One explicit exception may remain: the suppressed `androidx.core:core` version warning while `1.18.0` requires `minSdk 23` and the app supports `minSdk 21`. For distribution-sensitive changes, run `.\gradlew.bat lintFdroidDebug lintGplayDebug testFdroidDebugUnitTest testGplayDebugUnitTest assembleFdroidRelease assembleGplayRelease`.
- Refactors that only move unchanged wiring into thin helpers do not need new tests by default. Behavior changes do.

## Editing guidance

Use these guardrails as a change-specific checklist before editing or reviewing related areas. The detailed ownership map is in the Architecture section.

- Keep background route computation separated from main-thread state mutation. Preserve `nav/routing/NavigationRouteExecutor` rather than inlining thread management back into `NavigationService`.
- Keep BRouter transient-failure classification in `nav/routing/BRouterTransientFailureClassifier`, retry attempt/delay behavior in `NavigationRouteRetryPolicy`, and the default BRouter adapter in `nav/routing/NavigationBRouterRouteCalculator` so `NavigationRouteExecutor` stays focused on route task submission, callback handoff, executor shutdown, and wake-lock scoping.
- Keep Android service concerns delegated through the existing foreground/location/power/dispatch/broadcast helpers and Android adapters, and keep `NavigationSession` as a coordinator over focused session collaborators.
- Do not add a wake-lock renewal loop or reintroduce a session-lifetime wake lock to keep navigation alive; if a path needs a wake lock, scope it to the shortest critical section that actually needs CPU residency.
- If you change reroute thresholds, polling cadence, turn-alert timing, blocked-road escalation, or route-request lifecycle behavior, update the corresponding `nav/` tests.
- If you change guidance confidence rules, keep map-free use in mind and update tests around bearing trust, forward-look route bearing, direction-of-progress, turn suppression, and duplicate/imminent alert behavior.
- If you change navigation intent extras, update `nav/intent/NavigationRequestIntentContract` first and keep resume/start flows serialized through it instead of hand-copying extras.
- If you change startup permission/settings/battery-optimization flow, keep `nav/ui/NavigationActivity` thin, keep Android permission/settings/battery-optimization inspection in `android/startup/AndroidNavigationPreflight`, and update the startup/lifecycle tests.
- If you change BRouter request parameters, response parsing, or voice-hint mapping, inspect `brouter/`, `nav/routing/`, `nav/route/`, and `nav/directions/` together and keep mode-9 coverage aligned.
- If you change POI search or incoming intent handling, preserve coordinate entry, empty-field history suggestions, history-before-online precedence from the first typed character, shared search dispatch, and history behavior for externally opened locations.
- If you add or change direct Android framework, Google SDK, AndroidX service, BRouter/document-provider, notification, TTS, sensor, or other external API access, first decide whether a focused adapter is meaningful. It is meaningful when the code would otherwise leak external SDK types across packages, duplicate permission/version/deprecation handling, require Robolectric for policy tests, or make F-Droid/gplay behavior harder to audit.
- If you change location code, verify Android location framework references remain isolated to `vibro.navigator.android.location` with `rg -n "(^import android\.location\.|(^|[^A-Za-z0-9_.])android\.location\.)" app/src/main/java app/src/fdroid/java app/src/gplay/java app/src/test/java app/src/testGplay/java | rg -v "app/src/(main|fdroid|gplay|test|testGplay)/java[/\\]vibro[/\\]navigator[/\\]android[/\\]location"` and verify `LocationManager`, `LocationListener`, and `GnssStatus` with the same path exclusion. Also verify fused GMS references remain isolated to `app/src/gplay/java/vibro/navigator/android/location` and `app/src/testGplay/java/vibro/navigator/android/location`.
- If you change fused location, Google POI search, Android Auto, or distribution bridges, verify Google and Android for Cars references remain isolated to `app/src/gplay` and `app/src/testGplay`, and verify the F-Droid runtime classpath does not gain Play Services or Android for Cars dependencies.
- If you change Android Auto behavior, keep the Auto package as a template adapter over `NavigationService`/`NavState`, keep Auto strings in `app/src/gplay/res/values`, keep manifest, surface permission, and `automotive_app_desc.xml` declarations under `app/src/gplay`, and run both `assembleGplayDebug` and an F-Droid build to catch flavor leakage.
- If you change the map picker, preserve the no-external-library constraint, OSM raster tile rendering, current-location fallback when a field has no coordinates yet, restored-selection behavior across rotation, and the icon-only control layout. For map POIs, preserve user-initiated category discovery, single active category behavior, category counts, cached marker reuse from discovery responses, and missing-bounds-only Overpass fetches on pan/zoom.
- If you change logging, keep the shared `buildLogPrefix` plus `AppLogFiles.appendBlock` path intact so formatting, log-enabled gating, file-session selection, trimming, and legacy migration behavior stay consistent.
- If you change the stored data backup format, update `settings/AppDataBackup`, its tests, and the specification together so import/export compatibility and included data stores remain explicit.
- When extracting helpers around Android APIs, preserve lint-visible SDK guards with `@RequiresApi`, guarded callers, or min-SDK-safe overloads. In particular, avoid newer Java/Android overloads such as `URLEncoder.encode(String, Charset)` unless desugaring/minSdk support is already verified by flavor lint.
- If you change icon/theme/about assets, preserve the app identity: minimal, black-theme, vibration-first navigation.

## Architecture

- Main-screen code lives in `main/`. `main/MainActivity` should stay thin and delegate profile selection, stop rows, incoming intents, navigation input validation, BRouter install prompting, view binding, destination restore/save state, and map-picker request/result handling. Keep BRouter install dialog wiring in `MainActivityBRouterInstallPrompt`, destination/stop map-picker request codes and result application in `MainActivityMapPickerCoordinator`, main-screen widget lookup in `MainActivityControls`, destination field state persistence in `MainActivityDestinationState`, navigation input validation/history promotion in `NavigationInputResolver`, routing-profile spinner option construction and restore-position logic in `ProfileSpinnerOptions`/`ProfileSpinnerOption`, bundled-profile description metadata in `BundledProfileInfo`, and profile dropdown row rendering/info-dialog wiring in `ProfileSpinnerAdapter` rather than folding those state machines or row/UI details back into the activity or spinner controller.
- Map-picker screen code lives in `map/`. `map/MapPickerActivity` owns manual map-based point picking for destination and stop fields. Keep it dependency-light: use the existing local WebView asset approach for OpenStreetMap raster tiles instead of introducing a native map SDK unless explicitly requested. Keep current-location permission/provider/fresh-fix handling behind `android/location/AndroidMapPickerLocationController`, WebView JavaScript command construction in `MapPickerScriptController`, and intent/result extra serialization in `MapPickerIntentContract` so the activity stays focused on lifecycle, WebView setup, and result selection. Map POI overlay behavior belongs in the focused map helpers: keep dynamic Overpass category discovery/count parsing in the `OsmMapPoi*` parser/client classes, single-category UI state in `MapPoiCategorySelection`/`MapPoiOverlayView`, POI status timing in `MapPoiStatusController`, and selected-category marker caching/missing-bounds fetch minimization in `MapPoiLoader`/`MapPoiCache` rather than folding that logic into the activity or WebView asset.
- Navigation-screen code lives in `nav/ui/`. `NavigationActivity` should stay focused on service binding, startup coordination, route-export launch/error handling, and task/back-button behavior. Navigation-screen view binding, text scaling, compass mode rendering, GPS status rendering, and navigation-control click wiring belong in `NavigationActivityRenderer`; startup checks belong in `NavigationStartupCoordinator`; legacy plus predictive-back handling belongs in `NavigationActivityBackHandler`.
- Google Play Android Auto code lives in `app/src/gplay/java/vibro/navigator/auto`. Keep the Auto entry point as a thin Android for Cars template adapter over existing navigation state: `CarAppService` creates a session/screen, the screen binds to `NavigationService`, consumes `NavState`, renders the landscape-style guidance/compass surface, and invokes existing binder actions for blocked-road, pause/resume, and stop. Keep Android for Cars template construction in `ViBRoCarTemplates` so `ViBRoCarScreen` stays focused on lifecycle, service binding, state handoff, and surface invalidation. Do not duplicate route calculation, tracking, startup preflight, or guidance decisions in the Auto package. Keep `androidx.car.app.minCarApiLevel` as low as practical and use broadly supported templates unless a deliberate compatibility tradeoff is documented.
- Keep Auto surface drawing split across focused classes: a surface lifecycle coordinator, a layout painter, a text-column painter, a button-row painter, and a compass painter that reuses `NavigationCompassView`. Do not collapse surface lifecycle, Canvas layout, button hit testing, and compass rendering into one large Auto class.
- Treat pause/resume as real navigation-session state, not as a UI-only toggle. `nav/ui/NavigationActivity` and `NavigationActivityRenderer` should only render/invoke binder actions; the paused/running behavior must stay owned by `NavigationService` and `NavigationSession`.
- `nav/ui/NavigationActivity` must remain a platform `Activity`. If back behavior changes, preserve the current combination of legacy `onBackPressed()` handling plus platform predictive-back registration for API 33+ instead of switching the screen to `ComponentActivity`.
- The navigation screen's center visualization is a custom `nav/compass/ui/NavigationCompassView` fed by lightweight navigation state from `nav/model` and `nav/compass`. Keep route geometry preparation out of the view and keep Android drawing concerns out of the service/session logic. `NavigationCompassView` should compose compass chrome and delegate route drawing to `NavigationCompassRouteRenderer`, route start/destination/hint/intermediate-stop markers and destination-reached radius drawing to `NavigationCompassRouteMarkerRenderer`, route-start approach target drawing to `NavigationCompassRouteStartApproachRenderer`, route projection math to `NavigationCompassRouteProjector`, distance/time legend drawing to `NavigationCompassLegendRenderer`, stationary turn-to-face-route target drawing to `NavigationCompassOrientationCueRenderer`, and transient selected-heading-source calibration background state to `NavigationCompassCalibrationRing`. Paused-state compass chrome belongs in `NavigationCompassView` and should reuse the same outer compass layer geometry and transparency as the calibration background instead of drawing a separate outside ring. Compass route/hint/intermediate-stop sampling belongs in `nav/compass/CompassRouteGeometryFactory`; route-start approach target projection belongs in `nav/compass/CompassRouteStartApproachProjectionFactory`; automatic compass zoom/radius reuse/smoothing belongs in `nav/compass/CompassRadiusResolver`; lazy route-point projection belongs in `ProjectedCompassRoutePointList`. `NavCompassState` should expose its display contract through focused value objects: `CompassDisplayMode`, `CompassRadiusState`, `CompassProgressLabels`, `CompassOrientationCue`, and `CompassRoutePoint`; use named factories such as `fromProjectedPoints` and `fromRouteGeometry` with grouped construction inputs such as `NavCompassProjectedPointsInput` and `NavCompassRouteGeometryInput` instead of direct public constructors or long constructor chains. Destination distance and destination-reached radius display data belong in `CompassProgressLabels`; the destination-reached radius value should come from `NavigationRouteGeometryState` so compass rendering uses the same arrival threshold as notification/session arrival detection for both destination and intermediate-stop markers. Compass calibration warning/success chrome must reflect the heading accuracy carried by the selected displayed heading source, such as trusted GPS/course, movement-derived course, or live sensor heading, rather than raw heading-sensor calibration when that raw sensor is not the active display source.
- Display-relative compass heading preparation belongs outside `NavigationCompassView` in `nav/orientation`. Keep screen-rotation compensation and heading-accuracy mapping in `NavigationDisplayHeading`; keep heading-sensor lifecycle, stationary-orientation notification wiring, and compass UI refresh throttling in `NavigationOrientationController`; and keep raw heading-sensor output available for non-UI orientation logic such as stationary turn-to-face-route advice. Prefer rotation vector when the device exposes it, support geomagnetic-rotation-vector fallback devices, and use the deprecated orientation sensor only as a fresh calibration-status cross-check rather than as a heading source.
- `NavigationOrientationController` should be constructed from app-owned heading, display-rotation, elapsed-time, and UI-dispatch ports. Android wiring for those ports belongs in `android/orientation/AndroidNavigationOrientationControllerFactory`.
- `nav/service/NavigationService` is the Android lifecycle shell. Keep collaborator construction and controller attachment in `NavigationServiceDependencies`, grouped by `NavigationForegroundRuntime`, `NavigationTrackingRuntime`, and `NavigationRoutingRuntime`; expose those grouped runtime ports to the service shell through `NavigationServiceRuntime`; start/stop intent handling in `NavigationServiceCommandHandler`; route-recalculation request preparation/notification handoff in `NavigationServiceRouteRecalculator`; location/provider callback handling in `NavigationServiceLocationHandler`; bound-client adaptation in `NavigationServiceBinderHost`; route callback handoff in `NavigationServiceRouteCallback`; foreground-coordinator callbacks in `NavigationServiceForegroundHost`; screen/UI visibility and compass-dispatch gating in `NavigationServiceUiVisibility`; paused-state turn-event gating in `NavigationServiceTurnEvents`; and turn notification fan-out in `NavigationServiceTurnNotificationSink`/`nav/guidance/NavigationTurnEventDispatcher`. The bound-service API, blocked-road binder validation, and active-route GPX export handoff belong in `NavigationServiceBinder`. Spoken maneuver guidance belongs in `nav/voice`, with the service only owning lifecycle handoff and shutdown.
- Stationary turn-to-face-route notification episode state belongs in `nav/orientation/StationaryOrientationNotifier`, including the active `CompassOrientationCue` target-bearing lifecycle and movement-start dismissal. Keep `NavigationOrientationController` responsible for wiring lifecycle inputs, foreground notification sinks, and active cue exposure rather than moving the dwell/notify/reset policy into `NavigationService`.
- If pause/resume behavior changes, preserve the current contract that pausing retains the active request/route while suspending live location, reroute, and turn-notification processing until resume.
- Long-lived navigation reliability should come from the location foreground service and ongoing location callbacks, not from a session-long CPU wake lock.
- Any partial wake lock used by navigation must stay short, explicit, and owned in `nav/power` by the collaborator performing the critical burst of work, such as route or reroute calculation.
- `nav/session/NavigationSession` is the session-level coordinator. Keep filtered location, route progress, blocked-road state, turn progression, route display state, and route-request lifecycle split across dedicated state/policy classes instead of collapsing them back together. Keep session collaborator wiring in `NavigationSessionComponents`; raw-location-to-session-update evaluation in `NavigationSessionLocationEvaluator`; display-state assembly in `NavigationSessionStateBuilder`; and active-route GPX export in `NavigationSessionRouteExporter`. Keep the session handoff contracts in their focused packages: `nav/location/NavigationLocationUpdateResult`, `nav/routing/NavigationRouteRequestSnapshot`, `nav/session/NavigationRouteEvaluation`, and `nav/guidance/NavigationTurnEvent`. Within filtered location handling, keep recent filtered-fix motion history, stationary detection, speed fallback, and movement-derived bearing in `nav/location/NavigationLocationMotionModel` rather than folding those heuristics into `NavigationSessionLocationState`. Rolling route-progress samples for smoothed accuracy, ETA speed, and direction-of-progress evidence belong in `nav/guidance/NavigationRouteProgressTracker`. Heading-source selection for display state belongs in `NavigationSessionHeadingResolver`.
- `NavigationSessionRouteState` owns active-route coordination, not the full decision logic inline. Keep route-state collaborator wiring in `NavigationSessionRouteComponents`; route-location evaluation in `NavigationRouteEvaluator`; route evaluation results in `NavigationRouteEvaluation`; final destination-reached checks in `NavigationArrivalDetector`; intermediate-stop arrival and remaining-stop filtering state in `NavigationIntermediateArrivalTracker`; route-start approach activation state in `RouteStartApproachState`; blocked-road no-go selection in `NavigationBlockedPointSelector`; and route-result application/reset handoff in `NavigationRouteResultApplier`. Keep active route/polyline ownership, last-segment memory, destination-radius geometry, and route-bearing lookup in `nav/route/NavigationRouteGeometryState`; keep route-start approach planning in `nav/route/RouteStartApproach`; keep deviation policy, confirmation, along-track direction evidence, and reroute-notice logging in `nav/guidance/NavigationRouteDeviationHandler`; keep expected route-bearing lookahead in `nav/orientation/NavigationExpectedBearingResolver`; keep target progress labels and high-level route display branching in `NavigationSessionRouteDisplayState`; keep compass geometry/radius/accuracy display memory in `CompassDisplayMemory`; and keep `nav/model/NavState` construction in `nav/presentation/NavStateComposer` via `NavStateBuildInput` and `NavigationDisplaySnapshot` so route safety decisions and route presentation stay independently understandable. Memory mutation after rendering belongs in explicit display-advance paths such as `advanceDisplayState`, not hidden inside pure state-building helpers.
- Synthetic intermediate-arrival sequencing for turn notifications belongs in `nav/guidance/NavigationGuidanceHintSequence` and `NavigationGuidanceHintSequenceBuilder`, with `NavigationTurnState` coordinating the current pointer and notification flags. Do not fold intermediate-stop synthetic hint ordering back into `TurnEventPlanner`, `NavigationRouteEvaluator`, or UI text formatting; those layers should consume ordered guidance candidates or display candidates through their focused handoff APIs.
- Keep reroute heuristics split between bearing-source trust, route-deviation policy, deviation confirmation, and route-state progress handling in `nav/guidance`. Wrong-direction detection should continue to use forward-looking route bearing plus along-track direction-of-progress evidence instead of relying on a raw matched-segment bearing alone. Consecutive-sample confirmation and speed-sensitive immediate off-track margins belong in `NavigationDeviationConfirmation`.
- Startup last-known-location freshness and quality selection belongs in `nav/startup/NavigationStartupLocationSelector`, with shared last-known provider comparison and reader handoff in `nav/location/LastKnownLocationSelector`; keep `NavigationLocationController` focused on orchestrating app-owned location ports and active-subscription reuse. Provider permission checks, enabled-provider selection, last-known reads, and continuous update requests belong behind the `nav/location/NavigationLocationProvider` port. Android `LocationManager` calls, `LocationListener` callbacks, `GnssStatus`, and Android `Location` conversion belong only in `android/location`, including `AndroidNavigationLocationControllerFactory`, `NavigationLocationProviderAccess`, `NavigationCurrentLocationSeeder`, `NavigationGnssStatusTracker`, `AndroidLocationConverter`, `AndroidLocationListenerAdapter`, `AndroidLocationDiagnostics`, `AndroidLocationSettings`, `AndroidMapPickerLocationController`, and `NavigationLegacyLocationUpdates`. Android `Location` must be converted to app-owned `NavigationLocation` before leaving `android/location`; downstream freshness, routing, display, and diagnostics code must use `NavigationLocation`/`NavigationLocationFix` so selection policy tests do not need Robolectric. Foreground navigation GNSS satellite-count callback state belongs behind `NavigationGnssTracker`, with Android callback wiring in `android/location/NavigationGnssStatusTracker`. Flavor-specific fused-location adapters also belong in their source set under `android/location`; `distribution/DistributionServices` should select them but not own GMS API calls or no-op adapter implementations.
- Flavor-specific location/search capabilities are reached through `vibro.navigator.distribution.DistributionServices`. The `fdroid` source set must provide no-op/non-Google implementations. The `gplay` source set owns Google fused location, Google POI search, and Android Auto implementations, including all `com.google.android.gms`, Google Maps REST client/parser, and `androidx.car.app` usage. Common navigation code may depend on small interfaces such as `FusedLocationUpdateClient`, but it must not import Google or Android for Cars classes directly.
- `nav/model/NavigationRequest` is the pure domain request. The shared navigation extras contract used by activities, the service, and resume notifications belongs in `nav/intent/NavigationRequestIntentContract`; keep all start/resume serialization through that contract instead of hand-copying extras.
- `nav/model/NavState` is the immutable navigation display snapshot. Its public display contract should stay grouped by focused value objects: `NavRouteStatus`, `NavGuidanceStatus`, `NavProgressStatus`, `NavGpsStatus`, and `NavPauseStatus`. Do not reintroduce duplicate top-level aliases for guidance, progress, GPS, compass, or pause fields, and do not move Android/resource-aware state construction back into `NavState`. ## Local config

- Optional Google key for the `gplay` flavor only: save a Google Maps key in the app's About settings, validate non-empty keys through Google Maps Geocoding before marking them valid, and enable Google search only for saved valid keys. Do not bundle Google API keys into the APK.
- BRouter must be installed on the device as `btools.routingapp`
- The app may use a user-selected document tree for external custom `.brf` profiles
- Destination/stop map picking currently requires only platform WebView plus network access to `tile.openstreetmap.org`; do not replace it with an external map dependency unless explicitly requested
- `local.properties` is developer-local configuration. Do not make release or F-Droid flows depend on committed machine-specific values.
- Optional behavior logs are written under the app-specific external files `logs/` directory, preferring a removable memory card when one is mounted. On device, check `/storage/<card-id>/Android/data/vibro.navigator.debug/files/logs/` for debug builds and `/storage/<card-id>/Android/data/vibro.navigator/files/logs/` for release builds; if no removable card is present, check the same package paths under primary external storage such as `/sdcard/Android/data/.../files/logs/`.
